Pi Remote Engineering

Claude thinks.
Pi does the work.

Building a Claude SDK provider without handing over Pi's tools, instructions or history. The interesting part starts when the conversation needs to change.

Notes from building Pi RemoteUpdated October 19, 2026Experimental, with known gaps

Adding another model sounds like a plumbing job. Send a prompt, receive a response, connect a few tools. We wanted something stricter: changing the provider should not quietly change the agent you trust.

Your instructions should still matter. A denied write should stay denied. An edit that already happened should not happen again because a process restarted. And choosing an earlier conversation should not pretend the filesystem went back in time.

That is the project behind claude-sdk. The provider uses the official Claude Agent SDK and the existing Claude login, while Pi keeps authority over the work. Pi Remote is the phone interface, normally connected to the local host through opentunnel. The provider lives inside Pi, not in the browser.

A provider, not a second set of tools.

The SDK-managed Claude Code runtime has its own tools and lifecycle. We deliberately do not let that become a second executor beside Pi. Its built-in tools, built-in Agent tool, implicit MCP servers and native hooks are disabled on this path.

Instead, the adapter advertises Pi's current tool schemas through MCP. Claude proposes a call, Pi checks the arguments and permission policy, and Pi executes it. The waiting SDK handler receives the actual result under the matching call ID. Parallel calls can finish in different orders without swapping their results.

This sounds fussy until something fails halfway through. A real incident wrote a file successfully and then produced malformed JSON for an edit. The invalid edit never ran. The old bridge threw too early and replaced the useful failure with login advice.

Now arguments stay buffered until they form valid JSON, while text and thinking can still stream. A correction needs the exact SDK rejection and a fresh call ID. We do not guess what an invalid edit probably meant, or replay the successful write to make the conversation look tidy.

One executor. Current Pi tools, ordinary permissions, real results. MCP is the connection, not a shortcut around those rules.

Then we had two memories to keep honest.

Pi saves a conversation. The SDK also maintains a native Claude conversation. They overlap, but they have different jobs.

Pi's record is the durable audit: requests, calls, results, summaries, branches and usage. The native SDK context is the model conversation currently doing inference. A saved Pi chat can outlive several native contexts.

For a normal completed-checkpoint restart, the adapter verifies the accepted history and configuration before resuming the native context. A phone refresh mostly reopens the interface. Replacing the Pi worker tests a deeper boundary: can the provider restore the state that actually belongs to this chat?

A checkpoint cannot prove that an unfinished command succeeded. If a tool result is missing, the adapter must keep that outcome unknown. Explicit recovery is available only when its checkpoint and confirmation requirements are met. It is not a universal repair button.

There is also a retention consequence. Deleting a Pi chat does not automatically delete the separate SDK transcript. Tool-free helpers, such as title generation, use isolated queries and cannot reach the foreground chat's tools.

Changing the context must not repeat the past.

Compaction, branching and a changed tool set cannot always use the old native query. The useful abstraction turned out to be a validated handoff: preserve Pi's record, verify the boundary, then open a fresh native context for the selected model history.

For compaction and branches, a persisted receipt binds the source, new projection, configuration and owner before the next SDK checkpoint exists. A restart in that gap has something concrete to validate. Missing or altered metadata cannot silently approve an older context at a new position.

The model receives previous calls and results as labeled historical data. Their IDs are retired. Current schemas and permissions still govern any new calls. Private reasoning and opaque provider signatures stay out of the imported context, without disappearing from the original audit.

Four ways to change history, without changing what happened.

The operations look similar in a chat interface, but they make different promises. A clone copies a completed tip. A fork stops at an earlier point. Tree navigation changes the active path inside the same file. Compaction builds a shorter working context from a Pi-generated summary.

The comparison below uses one illustrative history. Change the operation and watch what the model receives. The file effects do not move.

Pi is the sole summarizer for production compaction, through its normal isolated, tool-free request. The native SDK's automatic and idle compaction stay disabled. Earlier native Haiku experiments lost remembered facts, often reducing a summary to ACK_0. Pi-owned compaction is a separate path, not a claim that the native failure was fixed.

Forks and tree moves have a second subtlety. A later completed checkpoint can sometimes prove an earlier queued or tool-boundary selection. The adapter carries only the necessary attested system checkpoint as configuration evidence, not the omitted later conversation.

A tree move can optionally include a Pi summary of the abandoned path. That deliberately carries some abandoned information into the destination. Without that summary, later private facts must remain excluded. Returning to a path opens another fresh native context; it does not rewind an old native transcript.

None of these operations rewinds the filesystem. Summaries, clones, forks and tree moves never undo a write, shell command or external effect. New work must inspect current state when that distinction matters.

The instructions are part of the contract.

The adapter uses Claude Code's official SDK preset with Pi's required instructions attached. Operator rules, project context, skills, tool schemas and extension sections do not become optional because another runtime is doing inference.

We did find one upstream request rejection sensitive to a generated documentation combination. The mitigation is structured prompt projection: proven generated identity boilerplate and the default documentation-routing index can remain Pi-side, while the SDK uses its own base preset. Custom prompts and explicitly supplied documentation stay intact.

Both the canonical Pi prompt and the SDK-facing projection are fingerprinted. Unaccounted rewrites fail before SDK startup. The mitigation does not explain or fix the upstream enforcement change, and it did not require changing billing, copying credentials or switching the default provider.

An earlier parent reload fix shows the same boundary. Pi had regenerated identical tool guidance in another order. We now allow that order-only change through the validated tool handoff, while changed or removed operator text and protected configuration changes remain checked. A new native query receives the current tools and instructions; it continues remaining work rather than repeating the loader.

The worker problem isn't finished.

A parent SDK chat is not the whole system. A worker is another Pi agent with its own prompt, tools and memory. Its native context must never be the parent's conversation in disguise.

Fresh foreground children using the builtin worker profile now have independent, temporary SDK bridges. They can read files, edit code and check their work. Parallel background workers and completion notices have also passed focused real-provider journeys.

The next failure came from a different builtin profile. A worker replaces the generated base with its role prompt, while delegate appends its role to that base. Both keep their configured project context. Two ordinary parallel delegates failed before either child reached the SDK: their safety hook had returned the whole prompt with additional child rules, which Pi treats as an opaque replacement.

The fix proves an exact prefix: the complete canonical Pi base, plus an unchanged suffix of child instructions. Only proven generated identity and default documentation can stay Pi-side. The appended child rules, operator instructions, project context and current tools remain intact. A changed base or explicit documentation cannot be quietly stripped to make the request pass.

The normal default-placement parallel flow now passes on Codex, SDK Haiku and SDK Opus. Each pair used real tools and inherited project rules; no profile or thinking downgrade was needed. That fixes fresh delegation, not retained continuation. Forcing append-mode delegates into a foreground route without their own SDK hooks remains outside this fix.

Here, foreground means an in-process child borrowing a provider registration. Background resume starts a separate Pi process with its own extension loading. This has nothing to do with moving your phone tab into the background.

The existing pi-subagents API can load the child's SDK hooks and save a checkpoint without modifying the extension. An upstream patch is therefore not proven necessary just to supply that lifecycle. Production use still needs care because the registration is parent-wide, permits one registration per parent and can conflict with another policy or a non-SDK agent's extension ceiling.

The remaining adapter work must preserve current instructions and accepted history in a validated fresh-context handoff. Dropping Ponytail or weakening the fingerprint would make a test green by changing the problem. Parent SDK chats themselves do not depend on pi-subagents.

Where that leaves us.

We have a provider with Pi-owned execution and a substantial parent-session lifecycle. Manual and threshold compaction, completed clones, earlier forks and validated tree moves have focused coverage. Separate real Codex, SDK Haiku and SDK Opus journeys passed those parent contracts.

That is useful evidence. It is not complete interchangeability. SDK retained-worker continuation remains red. Explicitly forced foreground delegates still lack child-owned prompt provenance. Broader instruction/configuration transitions remain guarded. Child-local lifecycle, nested/custom-agent combinations, overflow recovery, exhaustive partial writes, physical Safari and overnight stress still need evidence.

The underlying principle is simple enough to keep using: Pi owns what happened. A model context must match that record before it can continue.

The four history operations, precisely
Compaction
Same Pi file, shorter working context from Pi's summary plus kept history. Original audit stays. A summary is lossy; retaining tested facts does not prove perfect recall.
Clone
New Pi file from the completed tip. An owner-bound receipt prevents the new chat from resuming the parent's native query. The source stays unchanged by clone creation and clone-only work.
Fork
New Pi file before a selected user message. The message returns for editing, not automatic submission. Missing results, split tool batches and unsafe outgoing work remain blocked.
Tree
Another selected path in the same file, with optional Pi summary. Intent and destination receipts bind the move. Each move, including returning, opens a fresh native context. Failed or stopped summaries leave the outgoing path usable.

Receipts permit validated restart before the first new checkpoint. Missing or altered source, summary, ownership or configuration rejects. Controlled receipt gaps and some owned-worker SIGKILL boundaries were checked, not every partial write or power-loss scenario. These changes do not add new phone history controls or establish child-local lifecycle.

Stop, failures, recovery and safe restarts

Recorded cancellation with matching Pi results can rebuild a fresh native context on the next message in the same chat. This is not native pause/resume. A failed or cancelled tool may already have had effects.

Unknown SDK work and missing results cannot become invented successes. /sdk-recover requires a valid completed checkpoint and interactive confirmation, labels unknown outcomes as unknown and leaves the original audit intact.

Completion notices travel as the complete ordered trailing input group. Completed turns from another provider can be imported as data when returning to SDK Claude, without re-executing their tools.

A safe SDK host restart waits for final settlement and a saved checkpoint, with no pending tools or blocking dialogs. agent_end alone is not enough. Forced interruption can still leave unknown outcomes.

Models, images, reasoning and usage

The provider registers experimental Haiku, Sonnet and Opus models. Registration is not full-matrix verification. Pi effort controls map to SDK adaptive thinking; Off requests disabled reasoning, but emitted thinking does not prove zero reasoning.

Image attachments and image tool results travel as image blocks. Their focused checks do not establish every image/branch/delegation combination. New native contexts reset the native usage baseline, not Pi's prior totals. Nominal cost estimates are not a subscription balance or proof of the amount charged.

A few terms without the mystery
Native context
One Claude conversation managed by the SDK. It can be replaced without creating a new Pi chat.
Projection
The selected history sent to the model, which may be shorter than the full audit.
Accepted prefix
The initial Pi history that the saved SDK state has already accounted for.
Checkpoint
A completed continuation point binding native IDs, accepted history and configuration.
Receipt
Persisted transition evidence before the first new checkpoint.
Lifecycle hooks
Extension callbacks used to load and save provider state at session/turn boundaries.
Fingerprint
A hash that detects mismatches. It does not guess whether different instructions mean the same thing.
Replay
Repeating a past action is forbidden during history import. Test-peer replay is different: a deterministic substitute for the external SDK that exercises real Pi behavior.
