Claude SDK, with Pi still in control.

We built a Claude SDK provider for Pi. You can use Claude through the official Agent SDK while Pi keeps control of your tools, permissions, instructions and saved conversation.

One model provider. Pi still runs the work.

The provider is still experimental. Several realistic parent-chat workflows pass. Durable retained-worker continuation does not. There is no all-green full provider-parity run.

The goal is to change the model provider without giving up the normal Pi workflow. We have not reached complete interchangeability yet.

The hard part is making two conversation systems agree about what has already happened, especially after Stop, restart, compaction or a branch change.

Claude proposes. Pi decides and executes.

The SDK sees Pi's current tool schemas through MCP, the protocol used to expose tools to the SDK. An SDK tool handler waits for Pi's result. It does not run the command itself.

What changed for malformed tool calls?

A real failure wrote a file successfully, then supplied malformed JSON for an edit. The old bridge threw too early and gave misleading login advice. The new path requires the SDK's rejection for that exact invalid call, then permits a corrected call with a fresh ID. It never guesses the intended arguments. Missing rejection receipts, reused IDs and excessive malformed attempts stop the query.

Pi can also activate more tools during a chat. After subagents_enable, for example, the adapter validates the completed work and replaces the immutable SDK query with one that advertises the new tools. It asks for the remaining work, not a repeat of the loader.

One saved chat can span several native SDK conversations.

This is the most useful distinction in the whole design. A Pi conversation is the durable chat and audit you navigate. A native SDK context is a particular Claude conversation managed by the SDK. They are connected, but they are not the same object.

On a normal completed-checkpoint restart, the adapter verifies that Pi's accepted history and configuration still match before resuming the corresponding native context. A phone refresh mostly reopens the UI; replacing a Pi worker also tests provider-state restoration.

A chat can also contain completed work from another Pi provider. When you return to SDK Claude, the adapter validates those intervening turns and imports them as historical data. It does not run their old tools again.

What about models, images, reasoning and usage?
  • The provider registers experimental Haiku, Sonnet and Opus models. Model availability is not a claim that every model passed the full workflow matrix.
  • Pi reasoning controls map to SDK adaptive thinking and effort. Off requests disabled thinking, but an emitted thinking frame does not prove the model used zero reasoning.
  • Image attachments and image tool results travel as image blocks. Their focused checks do not establish every image-plus-branching combination.
  • Token and cost records preserve Pi's earlier totals across fresh native contexts. Nominal cost estimates are not a subscription balance or proof of the amount charged.
  • Titles and other tool-free helper calls use isolated SDK queries, not the foreground chat's state or tools.
Two stores have separate retention. Deleting a Pi chat does not automatically delete the SDK transcript. Ephemeral helper queries, such as title generation, are separate and cannot run the foreground chat's tools.

When the context changes, start fresh without repeating the work.

Resuming a native query is right only when its saved context is still right. Compaction, a new branch, a validated tool-set change and recorded cancellation need a different path.

A transition receipt records what was approved before the first new SDK checkpoint exists. On restart, missing or altered source, projection, ownership or configuration must reject rather than silently pick an older context.

Why not just copy the visible chat into a new query?

The visible messages are not enough. A retained tool call may have lost its result. A selected branch may contain different instructions. A copied native ID may belong to the source chat. The adapter validates Pi's structured projection and accepted configuration, retires historical tool IDs and keeps unknown outcomes explicitly unknown. Private reasoning and opaque provider signatures are omitted from imported context, not deleted from the original audit.

Four history operations, four different meanings.

These are implemented and focused-tested for saved parent conversations. They do not establish child-local lifecycle support or add new phone clone, fork or tree-picker controls.

Compaction keeps a shorter working context.

Pi generates the summary through its normal isolated, tool-free summarizer. The adapter validates the source and receipt, then gives a fresh SDK context the summary plus retained recent history.

SDK-native automatic and idle compaction stay disabled. Earlier native Haiku experiments lost remembered facts, often leaving an ACK_0 summary. Pi-owned compaction is a separate implementation, not a claim that the native failure is fixed.

A clone makes another chat at the completed tip.

A clone receives an owner-bound receipt in the new Pi file. Copying the parent's checkpoint does not authorize resuming the parent's native query under the new chat's identity.

A fork makes another chat from an earlier point.

A later completed checkpoint can sometimes prove an earlier queued or tool-boundary point. Only the necessary attested system checkpoint travels as configuration evidence. Omitted later user and assistant text does not travel with it.

Tree navigation moves inside the same Pi file.

The adapter saves navigation intent and then a destination receipt. It cannot silently reuse an old native context after an incomplete move. A failed or stopped summary leaves the original path usable.

History selection is never filesystem rollback. Cloning, forking, compaction and tree navigation do not reverse writes, edits, shell commands or external effects. New work must inspect current state when it matters.

Your instructions stay. Proven generated boilerplate takes a different route.

The SDK uses Claude Code's official base preset. The adapter attaches Pi's required instructions rather than pretending that an arbitrary rewritten prompt is equivalent.

This projection mitigates a content-sensitive upstream rejection. The same generated documentation combination could trigger an extra-usage-style error even though authentication had not changed. That does not establish a billing fix, explain the upstream enforcement change or justify copying credentials.

What did the latest parent reload fix change?

Pi can regenerate the tool list in a different order after restart without changing any declaration or non-tool instruction. The old guard rejected it because it expected a declaration change first.

The fix permits order-only regeneration when the exact guidance lines and declarations match, after reconstructing the old configuration. It still uses a fresh native context. Changed generated content, changed or removed operator overrides and protected configuration changes remain covered by rejection checks. All 17 focused tool cases passed on Pi 1.2 and 1.3.

Stop is different from an unknown outcome.

Recorded Stop, matched Pi results
The next message can rebuild a fresh native context in the same Pi chat. This is validated cancellation continuation, not native pause/resume.
Malformed tool arguments
No invalid Pi call executes. Require the exact SDK rejection and a corrected call with a new ID.
Several child completion notices
Forward the complete trailing input group in order. Do not mistake earlier notices for unfinished historical turns.
Missing result or unknown SDK work
Stop automatic continuation. Do not invent success or repeat the action just to fill the gap.
Explicit recovery, when eligible
/sdk-recover needs a valid completed checkpoint and interactive confirmation. It starts a new native context and labels unknown outcomes as unknown. It is not a universal repair command.

A cancelled or failed tool may already have changed something. A recorded error is not proof that no effects occurred. Recovery and continuation preserve that distinction.

When is a host restart safe?

For SDK turns, the host waits for both final settlement and a saved-checkpoint receipt, with no pending tools or blocking dialogs. Receiving an agent_end event alone is not enough. The restart helper queues a detached job and waits rather than stopping its own still-running shell call. Forced interruption can still leave unknown outcomes.

Fresh workers work. Durable retained-worker continuation is unfinished.

A worker is a separate Pi agent. It needs its own instructions, tools and provider state. It must not borrow the parent's SDK conversation or inherit private parent memory by accident.

Here, foreground means an in-process child borrowing the parent's provider registration. Background resume starts a separate Pi process with its own extension loading. This is about the agent runtime, not whether your phone tab is in the background.

The first isolation fix gave borrowed foreground workers independent, temporary SDK bridges. Normal fresh workers can read files, edit code and validate their changes. Parallel background workers and automatic completion notices also passed focused real-provider checks.

The next step must preserve the resumed worker's current instructions and accepted history through a validated fresh-context handoff. Removing Ponytail, ignoring the fingerprint or reusing the old native query under a different prompt would hide the problem.

A pi-subagents patch is not proven necessary. Its existing API can load the hooks and save the checkpoint without a dependency change. Production integration still needs care: requirements apply parent-wide, allow one registration per parent and can conflict with another policy or a non-SDK agent's extension ceiling.

Parent SDK chats do not depend on pi-subagents. That extension matters when you use its worker/delegation workflow.

What the evidence actually says.

There are two useful kinds of verification. Neither replaces the other.

Focused replay E2Es

Real Pi, RPC, persistence, provider, MCP and filesystem effects. Only the external SDK peer is replayed. These can reliably reproduce corrupt receipts, missing results and precise crash boundaries.

Real-provider journeys

Real model services, normal personal resources, normal worker profiles and a mobile browser. They verify actual memory, edits, permissions, Stop and restarts. They cost model usage and cover fewer combinations.

The honest boundary today.

Focused-verified Parent history lifecycle
Completed-checkpoint restart, Pi-owned compaction, completed clones, earlier forks and validated tree moves, within the documented cases.
Focused-verified Normal new work
Pi-owned tools, permissions, dynamic tool activation, recorded Stop continuation and selected fresh-worker/background-notice journeys.
Reproduced gap · SDK-3 Retained SDK worker continuation
Missing child-owned state on the temporary route. With hooks loaded, real prompt changes still block resume.
Guarded · SDK-4 Protected configuration changes
General instruction, environment and output-limit changes cannot transparently reuse a native query. Validated tool-only transitions are a narrower exception.
Mitigated · SDK-5 Upstream request rejection
Structured prompt projection handles the proven generated trigger. The upstream issue itself is unresolved.
Not established Broader parity
Child-local compaction/branches, nested/custom agent combinations, overflow recovery, exhaustive partial-write failures, physical Safari and overnight stress.

We have built the provider and a substantial parent-session lifecycle. The remaining work is making worker lifecycle and broader configuration transitions equally safe, then proving the complete shared workflow matrix.

A small glossary.

Provider
The integration Pi uses to talk to a model backend. Here, claude-sdk.
Native context
One model conversation managed by the Claude SDK. Replacing it does not necessarily create a new Pi chat.
Projection
The selected history Pi presents to the model. The full audit can contain more than the active projection.
Checkpoint
A completed continuation point linking native IDs, accepted Pi history and configuration.
Receipt
Persisted transition metadata binding a validated source to its new context and owner before a new checkpoint exists.
Lifecycle hooks
Extension callbacks at events such as session startup and turn completion. The SDK provider uses them to load and persist its checkpoints.
Accepted prefix
The initial part of Pi history the saved SDK state has already accounted for.
Fingerprint
A hash used to detect mismatched history or configuration. It is not a guess that two prompts mean the same thing.
Replay
For execution, repeating an old action, which context import must never do. For tests, replaying an external SDK peer to exercise real Pi behavior deterministically.
